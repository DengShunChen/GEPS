摘要

  • GEPS 原本只支援 NVIDIA（OpenACC + CUDA Fortran）。現在已能在 AMD MI300X 上完整執行並算出正確結果：六個積分步的 surf pres tend rms 與 CPU 版相差 1e-11 到 1e-14。
  • 數值移植完成時每步要 740 s，經過 15 項優化降到 2.21 s，比同一台機器上 32 核 CPU（10.5 s）快 4.75 倍。每一項改動後六步結果都逐位元相同。
  • 24 小時預報（144 步）已跑完：積分總時間 416 s，中位步時 2.28 s，VRAM 峰值 176.9 / 192 GiB。
  • 找到並整理 8 類 ROCm 工具鏈缺陷，做成 7 個獨立 PoC 給 AMD。AMD 新版編譯器 afar 24.3.0 修好其中 4 個，但 24 小時預報仍比 7.2.2 慢約 4%，正式環境維持 ROCm 7.2.2。
  • NVIDIA 參考值為 0.34 s/步，跑在 8 張 A100 80GB 上，GPU 數量是我們的 4 倍，所以兩者不能直接比較。

移植架構

原則是不改動 NVIDIA 的原始碼，讓同一份程式碼同時支援兩種 GPU。AMD 版在編譯時自動產生：

元件作用
cmake/acc2omp.py編譯期轉譯器（約 1600 行），把 src/nvidia/ 的 OpenACC 與 CUDA Fortran 轉成 OpenMP target offload。大部分數值修正與 kernel 結構優化都在這裡
src/rocm/AMD 專用的 shim（cudafor/NCCL/cuBLAS/cuFFT → HIP/RCCL/hipBLAS/rocFFT）、手寫替代 kernel（tile 化平流）、HSA 配置快取
job/regression.ksh執行環境：stack 大小、配置快取、SDMA、afar 分支、GEPS_TAUE 長預報

對 src/ 只有兩處例外，都經過同意：sflx_gpu.f90 陣列改固定大小（#15），以及 outsigs.f90、outsit.f90 加 external split（flang 24 相容）。

階段一：數值移植（18 層）

GPU 版一開始會崩潰，修好後又算出 NaN，再來是數字錯。我們逐層排除，問題歸成以下幾類：

類別層內容與修法
HIP stream 競態6, 7, 10, 17acc2omp 把 OpenACC 的 async 丟掉，造成四種形態：NCCL 集合通訊後沒等待、graph capture 內的 OpenMP kernel 沒被錄進 graph（NNMI 變成 no-op，是 NaN 的根因）、cudaMemsetAsync 與 kernel 競態、裸 NCCLCHECK 沒等待。修法都在 acc2omp
OpenACC 與 OpenMP 語意差異9, 12, 16, 17內層 private 被丟掉；exit data delete 不等於 map(delete:)；迴圈內純量 OpenACC 預設 firstprivate、OpenMP 預設共享；kernel 外初始化的 private 純量（深對流 val1/val2、sflx snoexp）要改成 firstprivate
指標與記憶體1, 2, 3reshape 後 memset、cudaMallocAsync 裸指標、graph replay 後 has_device_addr 失效
VRAM 耗盡4, 5, 13, 14DPX 分區、每個緯度一個 FFT plan（每個約 20 MB）、libomptarget 池子不歸還
裝置 stack18runtime 大小的 private 陣列在 stack 上互相覆寫，需要 LIBOMPTARGET_STACK_SIZE ≥ 49152
原始碼潛在 bug11, 18intgrt_gpu 傳錯 poly（graph capture 掩蓋了）、adjptqintp_gpu 越界讀、hdiffu 讀 host 端 wmax

最終驗證（2026-09-17）：積分第 1 步 sptend = 0.43807396825059497（CPU 0.4380739682505907），六步全部在 1e-11 以內；深對流觸發數 29,009，與 CPU 相同。

有三個推論後來被量測推翻（第 4、5、8 層的初判），handoff 裡保留了推翻的過程，避免後人重走。

階段二：效能優化（15 項）

每項改動只改一個變數，改完都跑完整 tau=1，並要求六步結果與上一版逐位元相同。

對數刻度。#14 之前另以同一個執行檔重新量過基準，為 2.38 s（run-to-run 差異）。

方法上的教訓

  1. 先量再下結論。過程中有六個看似合理的假設被量測推翻（例如「特徵向量是垃圾」其實是探針量錯）。假設和結論在紀錄裡要分開寫。
  2. 探針樣本要涵蓋目標。有一天內五個錯誤結論，都來自樣本沒有涵蓋問題所在的位置。
  3. 先建立 CPU 基準，再逐波數從兩端夾。數值問題是靠 CPU 與 GPU 逐常式、逐波數對照才定位到的。
  4. 「數值錯」常常是 stream 競態。四類競態看起來都像演算法錯誤。先搜尋產生碼裡沒被等待的 stream 操作，再提理論。
  5. 逐位元相同當驗收標準。這個標準在優化期間抓到一個編譯器 bug（巢狀 reduction）。
  6. 先看執行檔時間戳。有兩次建置失敗但舊執行檔照跑，差點當成實驗結果。
